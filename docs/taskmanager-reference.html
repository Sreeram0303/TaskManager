01Configuration Management

The idea: os.getenv returns raw strings (or None), fails late (crashes on first use, not at boot), and scatters config reads across the codebase. Pydantic's BaseSettings validates every value at startup — missing or malformed config refuses to boot, with a clear error, instead of surfacing at 3am in production.

Details

  • Priority: real env var > .env file > class default — dev/staging/prod need zero code changes.
  • settings = Settings() constructed once, at module import — a validated singleton, not re-parsed per call.
  • Type coercion is automatic: "False" in .env becomes a real Python bool, not a truthy string.

    REDIS_URL: str

Three objects, three separate questions. engine: how do I physically talk to the DB (pools connections — a taxi company, not a car built per ride). Base: how do my Python classes map to tables (a registry — every subclass "enrolls"). sessionmaker: how do I manage one transaction (a Session is a shopping cart tracking adds/changes, all-or-nothing at commit()).

Details

  • create_engine() is lazy — connects to nothing until the first real query.
  • Long-lived infra (engine/Base/factory) created once per app; Sessions are one per request, then closed.
  • Two requests sharing a Session = two strangers sharing one shopping cart.

Code — src/utils/db.py

engine = create_async_engine(url=settings.DB_CONNECTION.replace("postgresql://","postgresql+asyncpg://"))
LocalSession = async_sessionmaker(bind=engine, expire_on_commit=False)

class Base(DeclarativeBase):
    pass

async def get_db():
    session = LocalSession()
    try:
        yield session          # request handling happens here
    except Exception:
        await session.rollback()
        raise
    finally:
        await session.close()  # same setup→yield→cleanup shape as middleware/lifespan
03Declarative Models (2.0 style)
Foundations
Mapped[int]Python-side truth
infers
column type
mapped_column()DB-only extras
real table column

The old Column style was writing DDL in Python clothes — no autocomplete, no type checking. 2.0 style: write an ordinary typed class, annotate DB-only details on the side. Mapped[str | None] reads exactly like an Optional field in a Pydantic DTO — nullability lives in the type itself.

Details

  • Mapped[X] = what the attribute is in Python; SQLAlchemy infers the SQL type from it.
  • mapped_column(...) = extras only (primary_key, ForeignKey, unique) — omit entirely if there are none.
  • Querying: select(Task).where(...) via session.execute — session.query() is the legacy 1.x idiom.

Code — src/task/models.py

class Task(Base):
    __tablename__ = "user_tasks"
    id: Mapped[int] = mapped_column(primary_key=True)
    user_id: Mapped[int] = mapped_column(ForeignKey("users.id", ondelete="CASCADE"))
    title: Mapped[str] = mapped_column(String(100))
    description: Mapped[str | None]         # nullable — the | None IS the schema
    is_completed: Mapped[bool] = mapped_column(default=False)
    owner: Mapped["User"] = relationship(back_populates="tasks")

Mental model — a shopping mall: app is the building; each APIRouter is a store organizing its own shelves without knowing its floor. include_router is the mall assigning the unit number, prepending the prefix. Routes inside a router are written relative — @router.get("/{id}"), not "/tasks/{id}".

  • Solves file organization and dependency direction — features never import main.py; main.py assembles features.
  • from main import app inside a feature file = circular import, the exact design this pattern prevents.
  • Forgetting include_router → the router silently doesn't exist. Same "registered nowhere" bug family as a forgotten migration import.

Pydantic's default read protocol is keys (data["title"]) — its home turf is the JSON boundary. ORM objects store data as attributes (task.title). from_attributes=True grants a second protocol: "not a dict? try getattr on each field instead."

Phase B — Auth Core
06Password Hashing
Auth Core
plaintext password
random saltborn at hash time
argon2idslow + memory-hard
PHC string$argon2id$v=19$m=...$salt$digest
stored in users row

Threat model: assume the DB eventually leaks. The question isn't "prevent the breach," it's "what does the attacker get." Hashing is one-way — meat grinder analogy: mince never becomes steak again, but two batches from the same cut match. Argon2id over bcrypt/sha256 specifically because it's memory-hard — GPU farms can't feed thousands of parallel cores enough RAM per guess.

Details

  • Salt's job is uniqueness, not secrecy — kills rainbow tables, lives inside the PHC string itself, right in the row.
  • Verify uses constant-time comparison — naive == leaks timing side-channels.
  • CPU-bound → wrapped in run_in_threadpool at the call site, never awaited eagerly (a real bug caught by the test suite — see 20).

Code — src/utils/security.py

password_hash = PasswordHash.recommended()   # policy, not hand-picked crypto params

def hash_password(password: str) -> str:
    return password_hash.hash(password)

def verify_password(password: str, hashed: str) -> bool:
    return password_hash.verify(password, hashed)   # constant-time internally
07JWT Access Tokens
Auth Core
header{alg: HS256}
payload{sub, exp, type}
HMAC_SHA256(header.payload, SECRET)
header.payload.signature

Festival wristband, not a guest list: the server writes a signed note once, the client carries it, the server verifies its own signature instead of a DB lookup every request. The payload is readable by anyone (base64, not encryption) — the signature makes it tamper-proof, not secret. Claims carry identifiers, never secrets.

Details

  • sub must be a string (RFC 7519) — proven live: pyjwt mints sub: 2 fine but rejects it on decode.
  • Must use datetime.now(timezone.utc) — a naive local datetime silently makes tokens live hours too long.
  • options={"require": ["exp","sub"]} — without it, a token with no exp is immortal.

Code — src/utils/security.py

def create_access_token(user_id: int) -> str:
    payload = {
        "sub": str(user_id),                                  # str at the boundary
        "exp": datetime.now(timezone.utc) + timedelta(minutes=settings.JWT_ACCESS_EXPIRE_MINUTES),
        "type": "access",
    }
    return jwt.encode(payload, settings.JWT_SECRET_KEY, algorithm=settings.JWT_ALGORITHM)

Three guards, each strictly dumber than the next, each unreachable unless the previous passed. HTTPBearer knows only HTTP headers (a bouncer's reflex). jwt.decode knows crypto and claims. The final DB check knows application state. The endpoint inherits all three guarantees as one typed parameter.

Details

  • 401 = identity claim failed (any reason, including "user no longer exists" — don't leak which). 403 = identity established, access denied (inactive).
  • Depends() resolves twice in time: once at startup (builds the graph, marks OpenAPI security), once per-request (leaves-first, cached — get_db appearing twice in the tree still runs once).

Code — src/utils/dependencies.py

async def get_current_user(credentials: BearerCredentials, db: DbSession):
    payload = decode_token(credentials.credentials)
    if payload.get("type") != "access":
        raise HTTPException(401, "Invalid token type")   # refresh token ≠ bearer credential
    user = await db.get(User, int(payload["sub"]))
    if not user: raise HTTPException(401)
    if not user.is_active: raise HTTPException(403, "User account is inactive")
    return user

CurrentUser = Annotated[User, Depends(get_current_user)]
09Refresh Token Rotation + Reuse Detection
Auth Core
ClientServer
Client→ServerPOST /refresh (old token)
Server↻Servermark old token revoked = True
Server⇢ClientNEW refresh + access token
attacker replays the OLD token later
Client→ServerPOST /refresh (old, already-revoked token)
Server⇢Client401 + REVOKE ALL sessions for this user

Every refresh mints a brand-new token and revokes the one just used. A revoked token being presented again is a strong signal of theft — not "expired," stolen and now in two hands — so the response isn't just "deny," it's "kill every session this user has."

Details

  • jti (unique, not secret) identifies the row; a separate CSPRNG-backed value would be needed if the token itself had to be unguessable server-side.
  • Real bugs caught building this: db.add(RefreshSchema(...)) instead of the ORM model; a missing payload["type"] == "access" check let refresh tokens work as permanent bearer creds.

if token_row.revoked:

token_row.revoked = True   # rotate: this one is now spent

11httpOnly Cookies

Browser

A cookie is data the server asks the browser to store and reattach automatically — nobody re-sends it manually, which is both the point and the risk. The refresh token (a 7-day credential) moved here specifically because httponly=True blocks any JS — yours, a library's, an XSS payload — from reading its value at all. The access token can't get this treatment: client JS must read it to build the Authorization header, so it's contained by short expiry instead.

Details

  • Four attributes, one job each: httponly (blocks JS reads), secure (HTTPS-only transport), samesite (the CSRF-relevant knob), path (scopes which URLs get it).
  • Real bug caught live: a cookie path scoped to /users/refresh silently never reached the sibling route /users/logout — fixed by picking the narrowest common-ancestor path, /users.

Code — src/user/router.py

response.set_cookie(value=token_payload["refresh_token"], key="refresh_token",
    httponly=True, secure=settings.COOKIE_SECURE, samesite="lax",
    path="/users", max_age=settings.JWT_REFRESH_EXPIRE_DAYS*24*60*60)
12CSRF — Double-Submit Cookie
Web Security
Browser (auto)Page JS (manual)Server
Two INDEPENDENT channels must agree
Browser→ServerCookie: csrf_token=abc (auto-attached)
Page JS→ServerX-CSRF-Token: abc (read via document.cookie, sent manually)
Server↻Servercookie value == header value?
Server⇢Page JSmatch → proceed / mismatch → 403

The server generates a random token at login and then forgets it — no DB row, no session store. The whole check is one line: does the incoming cookie equal the incoming header, right now. It works because a forged cross-site request can trigger the automatic channel (the cookie) but can't replicate the manual one — evil.com's JS calling document.cookie for a domain it isn't running on gets nothing, by the browser's own same-origin rule.

Details

  • secrets.token_urlsafe(32), not uuid4() — this token's job is being unguessable, not merely unique.
  • secrets.compare_digest(None, None) raises TypeError, doesn't return False — the most common real request (no CSRF header yet) would 500 without a short-circuit guard.
  • dependencies=[Depends(verify_csrf)] — a bare function in that list crashes the whole app at import time, not just the route.

Code — src/utils/dependencies.py

def verify_csrf(csrf_token: Annotated[str|None, Cookie()] = None,
                 X_CSRF_Token: Annotated[str|None, Header()] = None):
    if not csrf_token or not X_CSRF_Token or not secrets.compare_digest(csrf_token, X_CSRF_Token):
        raise HTTPException(403, "CSRF token missing or invalid")   # short-circuit BEFORE compare_digest
13CORS

A browser story, not a server story — curl/Postman/TestClient never see CORS at all. Same-Origin Policy blocks cross-origin JS from reading a response by default; CORS headers are the server opting out of part of that lockout for named origins. Not auth — it decides which pages' JS may read responses, not who may access data.

Details

  • allow_origins=["*"] + allow_credentials=True together is rejected outright by browsers — genuinely not an option once real cookies are in play.
  • Multi-middleware ordering rule, verified both directions: last registered = outermost, first to see the request, last to touch the response.

14Security Headers
Web Security
any request

X-Frame-Options: DENY

Strict-Transport-Security

Browser-enforced instructions, stamped on every response — textbook "for every request" middleware. nosniff stops a browser guessing a different content type than declared. X-Frame-Options: DENY closes off clickjacking (a real target here: /docs' own "Execute" button, invisibly framed). HSTS closes the SSL-stripping window on a user's very first plaintext request.

Details

  • CSP deliberately skipped — this app only returns JSON, no script-execution surface for a content policy to restrict.
  • HSTS gated behind settings.COOKIE_SECURE — sending it on plain localhost dev could make a browser refuse to connect at all for the whole max-age window.

Code — src/utils/security_headers.py

async def add_security_headers(request: Request, call_next):
    response = await call_next(request)
    response.headers["X-Content-Type-Options"] = "nosniff"
    response.headers["X-Frame-Options"] = "DENY"
    if settings.COOKIE_SECURE:
        response.headers["Strict-Transport-Security"] = "max-age=63072000; includeSubDomains"
    return response
15HTTPS / TLS
Web Security
BrowserCaddy / LB (holds cert)FastAPI app
Browser→ProxyTLS handshake, verifies cert against trusted CA
Browser→Proxyencrypted request
Proxy→AppPLAIN http, internal network only
App⇢Proxyplain response
Proxy⇢Browserre-encrypted response

HTTPS = HTTP wrapped in an encrypted tunnel — app code never changes. Asymmetric crypto bootstraps a shared symmetric session key once (slow, used briefly); everything after uses fast symmetric encryption. A certificate is a passport analogy: a CA signs "this domain owns this public key" with its own private key; the browser verifies that signature locally against a CA it already trusts. TLS terminates at a reverse proxy, not inside the FastAPI process — the internal hop stays plain HTTP because it never leaves a trusted network boundary.

Details

  • ACME (Let's Encrypt) proves domain control via a challenge — e.g. serve a specific token at /.well-known/acme-challenge/<token> — then signs automatically, no human review.
  • localhost is structurally unreachable from outside — real deployment needs an actually different, internet-routable machine.

The one app-code change this topic produces

secure=settings.COOKIE_SECURE   # False in dev, True once genuinely behind HTTPS — nothing else changes

The waiter analogy: bring the food first, update the inventory sheet after. The criterion: background what the response merely triggers; foreground what it asserts. Email on register — the 201 means "account exists," true at commit, the email arriving later changes nothing. Hashing — never; the 201 semantically asserts "credential stored."

Details

  • Dies with the process — no retries, no persistence. A restart mid-send = the task silently never existed. Loss-tolerable work only.
  • Anything that outlives the request must open its own DB session — the request's get_db session isn't guaranteed to still be usable.

20Async SQLAlchemy
Data & Performance

asyncpg — real non-blocking I/O

Once one function in the chain is async, every caller up the stack has to await it — "async is contagious." The reward: one process serves many requests concurrently by yielding the CPU during any real wait, instead of dedicating a thread per in-flight request.

Details

  • A genuine authbypass caught by the test suite mid-conversion: a threadpool-wrapped verify_password call missing its await — an un-awaited coroutine is always truthy, so the password check silently stopped doing anything at all.
  • expire_on_commit=False is the standard async pattern — without it, reading an attribute right after commit becomes a silent, impossible-in-async lazy reload.

21Cascade Deletes (passive_deletes)
Data & Performance
db.delete(user)

No (default) →

UPDATE tasks SET user_id=NULL
Postgres rejects — NOT NULL violation
Yes →

Two independent layers. ondelete="CASCADE" is a real Postgres constraint — enforced no matter what deletes the row, even raw SQL. passive_deletes=True is purely SQLAlchemy-side — it stops the ORM from trying to manage the cascade itself first. Verified live, both directions: without it, deleting a user genuinely crashes, not just runs an extra query.

Details

  • The failure mode without it: SQLAlchemy defaults to nulling out each child's FK before the parent delete — rejected outright since user_id isn't nullable.
  • A raw DELETE FROM users WHERE id=5; typed into psql would cascade correctly with or without this setting — it only governs SQLAlchemy's own Python-side behavior.

22N+1 Queries & Eager Loading
Data & Performance
for user in users: user.roles
1 query for users
+ 1 query PER user for roles
selectinload(User.roles)
1 query for users
+ 1 query for ALL roles, batched (IN ...)

Lazy loading is attribute access that secretly does I/O — fine in sync code, structurally impossible to do silently in async code (SQLAlchemy crashes with MissingGreenlet rather than freeze the whole event loop). N+1 is what happens when that lazy fetch is triggered once per parent, inside a loop, instead of once, batched, before the loop.

Details

  • selectinload: 2 queries total, regardless of N — right default for to-many relationships.
  • joinedload: 1 query via SQL JOIN, but duplicates parent columns once per child on to-many — better suited to to-one.
  • Full audit of this app found zero active N+1 bugs — every response DTO stays deliberately flat, never serializes a nested relationship.

Code — the exact live bug this app hit

# crashed: MissingGreenlet — user already persisted, roles not loaded

Read path: check cache, fall through to DB on miss, write back with a TTL. Write path: invalidate (delete) the key after the DB commit succeeds. Every Redis call wrapped in a resilience guard — a cache outage degrades to "always hit the DB," never fails the request outright.

Details

  • Deliberately scoped to the list endpoint only, not single-item fetches — those are already a fast PK lookup, caching them doubles the invalidation surface for little gain.

27Ticket-Based Realtime Auth
Realtime

Client→ServerPOST /realtime/ (real Bearer token, normal fetch)

EventSource can't set an Authorization header, so the real access token can't ride along — and putting it in a URL means access logs, browser history, Referer leaks. The fix: mint a deliberately weak, 30-second, single-use ticket using the real token over a normal fetch first — a coat-check tag, not your ID.

Details

  • GETDEL — atomic read-and-delete in one step, so a ticket can never be redeemed twice even under concurrent requests.
  • Short TTL and single-use together, not either alone — the ticket is only ever dangerous for the few seconds between minting and redemption.

def require_permission(permission_name: str):
    async def _require_permission(current_user: CurrentUser, db: DbSession):
        stmt = (select(Permission.id)
            .join(role_permissions, Permission.id == role_permissions.c.permission_id)
            .join(Role, Role.id == role_permissions.c.role_id)
            .join(user_roles, Role.id == user_roles.c.role_id)
            .where(user_roles.c.user_id == current_user.id, Permission.name == permission_name))
        if (await db.execute(stmt)).first() is None:
            raise HTTPException(403, "Insufficient permissions")
    return _require_permission

The "for every request" trigger — cross-cutting infrastructure, not a per-route opt-in. call_next isn't "the next single step" — calling it runs everything downstream, all the way to the endpoint and back, handing back the fully-built response for your own "after" code to still modify before passing it further out.

Details

Code — src/utils/logging.py

async def log_requests(request: Request, call_next):
    request_id_var.set(str(uuid.uuid4()))   # fresh per request, NOT module-level
    response = await call_next(request)      # runs the entire rest of the app
    logger.info(f"{request.method} {request.url.path} -> {response.status_code}")
    return response
